# 모바일 디자인 품질 게이트

## 목적과 적용 범위

이 문서는 잇츠미 모바일 화면이 구현 완료로 선언되기 전에 반드시 통과해야 하는 디자인
검증 절차다. 기능이 동작하는지만 확인하지 않고, 사용자가 `프로필을 완성해야 한다`는 압박
없이 짧은 기록도 온전한 자기소개로 느끼는지 실화면으로 확인한다.

`docs/product/vision.md`, `docs/product/principles.md`, `docs/product/mvp.md`,
`docs/design/prototype-v1.md`, `docs/design/brand.md`,
`docs/design/redesign-sprint-2.md`가 상위 기준이다. 이 문서는 상위 기준을
대체하지 않으며, 구현과 명세 사이의 차이를 발견하고 승인하는 출고 게이트로 사용한다.

적용 대상은 인증, 나, 질문, 기록 상세·편집·삭제, 변화, 공개 선택, 공개 미리보기, 방문자
공개 프로필과 계정 화면이다. 새 화면이나 새 상태가 추가되면 같은 작업 안에서 이 문서의
캡처 매트릭스에도 행을 추가한다.

## 품질 판단 원칙

1. 사용자의 문장이 시스템 장식, 카테고리, 날짜와 조작보다 먼저 읽혀야 한다.
2. 비어 있음은 부족이나 미완성이 아니라 `지금은 말하지 않기로 한 상태`로 보여야 한다.
3. 저장, 수정, 삭제와 공개는 서로 다른 결정이며, 공개는 실제 결과를 본 뒤에만 확정한다.
4. 과거와 현재의 차이는 보여주되 좋아짐, 나빠짐, 상승, 하락으로 판정하지 않는다.
5. 사진이나 긴 글이 없어도 활자, 여백과 절제된 범주 단서만으로 개인 화면이 완성되어야 한다.
6. 색, 장식과 모션은 의미를 보조할 뿐 상태를 단독으로 전달하거나 사용자 기록을 압도하지 않는다.
7. 좋아요, 팔로워·팔로잉 수, 조회수, 인기 순위, 궁합·성장 점수, 프로필 완성률, 경쟁형 연속
   기록은 제안·시안·구현·실험 어디에도 넣지 않는다.

## 책임과 승인 흐름

| 단계 | 책임 | 필수 산출물 | 통과 조건 |
| --- | --- | --- | --- |
| 설계 준비 | Product Designer | 화면 목적, 정보 우선순위, 상태 목록, 레퍼런스 기록, 변경 명세 | PO가 제품 정책 영향을 확인하고 Frontend가 구현 가능성을 확인함 |
| 구현 자체 점검 | Frontend | 같은 커밋의 상태별 실화면 캡처, 자동 검사 결과, 알려진 차이 | 필수 캡처와 체크리스트가 빠짐없이 채워짐 |
| 디자인 QA | Product Designer | 명세 대비 차이 목록, 심각도, 승인 또는 반려 결정 | Blocker와 Major가 0건이고 Minor가 기록됨 |
| 독립 검토 | Reviewer | 개인정보, 접근성, 회귀 위험 검토 | 개인정보 노출과 접근성 핵심 여정 실패가 0건임 |
| 최종 범위 결정 | Main/PO | 수용한 차이와 후속 작업의 근거 | 제품 정책 변경을 디자이너가 독단적으로 확정하지 않음 |

디자이너 승인은 설명이나 코드 리뷰만으로 대체할 수 없다. 승인 대상 커밋의 실화면과 실제
조작 결과를 확인해야 한다. 수정 후에는 수정된 화면뿐 아니라 공유 토큰·컴포넌트를 사용하는
인접 화면도 다시 캡처한다.

## 실화면 증거 규격

### 필수 뷰포트

- `390×844`: 기본 모바일 기준. 콘텐츠 폭은 좌우 20pt gutter를 제외한 350pt다.
- `430×932`: 큰 모바일 기준. 콘텐츠 폭은 좌우 24pt gutter를 제외한 382pt이며 다열로
  바뀌지 않는다.
- 출시 대상이 iOS와 Android 모두라면 두 플랫폼에서 각각 검증한다. 플랫폼별 전체 캡처가
  어려운 내부 반복에서는 한 플랫폼으로 전체 매트릭스를 검증하고, 다른 플랫폼에서 인증,
  나, 질문 입력·키보드, 공개 미리보기의 정상·오류·200% 확대를 최소 교차 검증한다.
- Web preview는 보조 증거일 뿐 네이티브 실화면을 대체하지 않는다.

`실화면`은 해당 커밋의 앱을 시뮬레이터, 에뮬레이터 또는 실제 기기에서 실행해 OS safe area,
번들 폰트, 실제 아이콘, 키보드와 하단 내비게이션까지 포함해 캡처한 화면이다. Figma 프레임,
Storybook, 잘린 컴포넌트 이미지, 브라우저 개발자 도구의 정적 DOM 캡처는 실화면 증거로
인정하지 않는다.

### 캡처 메타데이터와 파일명

각 검토 묶음에 다음을 기록한다.

- commit SHA, build 번호, 캡처 일시, OS와 앱 버전
- 기기·뷰포트, pixel ratio, 글자 크기, 밝은/고대비 모드, 축소 모션 여부
- fixture 이름과 데이터 조건: 기록 수, 공개 범위, 답변 길이, 오류 종류
- mock인지 실제 API인지와 사용한 locale
- 기준 명세와 의도적으로 남긴 차이의 링크

파일명은
`{screen}--{state}--{platform}--{width}x{height}--{font-scale}.png` 형식을 사용한다.
예: `me--empty--ios--390x844--100.png`,
`share--error--android--430x932--200.png`.

캡처는 화면 상단만 남기지 않는다. 스크롤 화면은 상단, 핵심 중간 상태와 마지막 CTA가
보이는 하단을 함께 제공하거나 한 장의 scroll capture를 제공한다. 입력 화면은 키보드가
닫힌 상태와 열린 상태를 모두 확인한다.

## 화면·상태 캡처 매트릭스

아래 상태는 `390×844`와 `430×932`에서 각각 캡처한다. `확대`는 OS 글자 크기 200% 또는
React Native `fontScale` 2.0을 뜻한다. 적용할 수 없는 상태는 빈칸으로 두지 않고 `N/A`와
근거를 기록한다.

| 화면 | 정상 | 빈 상태 | 로딩 | 오류·재시도 | 200% 확대 | 추가 필수 상태 |
| --- | --- | --- | --- | --- | --- | --- |
| 인증 | 유효 입력 전 기본 화면 | 입력값 없음 | 로그인 중 | 필드 오류, 인증 실패 | 키보드 열림 포함 | 비밀번호 보기·숨기기, 계정 제한 |
| 나 | 짧은 기록 3개 이상 | 기록 0개 | cover·장면 skeleton | 초기 불러오기 실패 | 긴 이름·intro·답변 포함 | 나만 보기와 공개 혼합, 긴 답변 |
| 질문 | 선택형과 자유 서술형 | 답 미선택 | 질문 불러오기·저장 중 | 불러오기·저장 실패 | 키보드와 600자 답변 포함 | 선택됨, 직접 쓰기, 건너뛰기 |
| 기록 상세 | 현재·과거 버전 있음 | 맥락·다음 시도 없음 | 상세 skeleton | 권한 없음·찾을 수 없음 | 긴 버전 3개 이상 | 편집, 공개 기록 수정 안내 |

| 변화 | 버전 2개 이상 | 비교할 과거 없음 | timeline skeleton | 불러오기 실패 | 날짜·메타 세로 쌓임 | 긴 변화 이유·다음 시도 |
| 공개 선택 | 공개·비공개 혼합 | 저장 기록 0개 | 목록 skeleton | 불러오기·저장 실패 | 긴 답변 포함 | 공개 전 확인, 공개 해제 확인 |

| 방문자 공개 프로필 | 공개 항목 있음 | 공개 항목 없음 | visitor 구조 skeleton | 잘못된 주소·서버 오류 | 긴 공개 콘텐츠 | 비공개 항목 부재 확인 |
| 계정 | 기본 계정 정보 | 선택 정보 없음 | 처리 중 | 요청 실패·세션 만료 | 긴 이메일·안내 포함 | 로그아웃·계정 회수 확인 |

모든 캡처 묶음에는 다음 개인정보 fixture를 함께 둔다.

- 소유자 응답: 공개 2개, 나만 보기 2개, 과거 버전과 작성 맥락이 있는 기록
- 방문자 응답: 공개 2개만 존재하며 내부 ID, 비공개 범주 자리표시, 과거 버전, 작성 맥락,
  이메일과 계정 상태가 없음
- 미리보기와 방문자 화면: 같은 공개 응답을 같은 렌더러로 표시해 문장, 순서와 빈 상태가 일치함

## 화면별 육안 점검

### 나

- 첫 시선이 실제 이름과 사용자 문장에 닿고, 날짜·로고·계정·공개 행동이 경쟁하지 않는다.
- cover는 고정 280pt를 사용하지 않는다. 390pt 기준 너비 350pt, padding 24pt, 자연 높이
  152–220pt를 기준으로 하며 이름·intro·대표 문장이 길어지면 상한 없이 늘어난다.
- 첫 viewport에서 실제 이름·intro와 대표 문장 1개 또는 다음 문장의 시작이 읽혀야 한다.
- 기록은 좌측 register와 1pt rule을 사용한 `FolioEntry`를 기본으로 한다. 최근 문장이 cover에
  먼저 보여도 우열·추천으로 표현하지 않고 목록에서 같은 문장에 다시 접근할 수 있어야 한다.
- 빈 화면은 여섯 개 슬롯, `0/6`, 완성률 없이 한 개 안내 모듈과 한 개 주요 행동으로 끝난다.
- 긴 답변은 100% 글자 크기에서 다섯 줄과 `이 문장 이어 읽기`를 제공하고 200%에서는 제한을 제거한다.

### 질문

- 한 화면에는 질문 하나만 있고 진행 막대, 번호, 완료율이 없다.
- 질문, 선택지, 입력, 안내와 CTA의 좌우 기준선이 모두 같고 너비는 콘텐츠 영역의 100%다.
- 선택지는 분리된 rounded radio card가 아니라 하나의 `ChoiceList` 안에서 1pt rule로 나뉜다.
  선택 상태는 Indigo Wash, 좌측 4pt register, 체크 아이콘과 `선택됨` 의미가 함께 전달된다.
- 선택 전 disabled 저장 CTA가 화면을 점유하지 않는다. 선택 후 `나만 보기로 남기기`가 질문
  흐름 안에 나타나며 질문과 두 개 이상의 선택지가 첫 viewport에서 읽힌다.
- 자유 입력은 최대 길이와 현재 글자 수를 연결해 알리고, 저장 실패 후에도 입력과 키보드
  문맥을 잃지 않는다.
- 600자 최대 답변을 입력한 채 200% 확대와 키보드가 동시에 적용돼도 질문, 현재 글자 수,
  오류, 저장과 건너뛰기 행동을 가로 스크롤 없이 순서대로 읽고 조작할 수 있어야 한다.
- `나만 보기` 안내가 저장 CTA 가까이에 있고, 저장·건너뛰기·닫기·나중에 수정이 가능하다.

### 기록 상세·변화

- 현재 답, 이전 답, 변화 이유와 다음 시도의 위계가 구분되며 앱이 변화의 방향을 평가하지 않는다.
- 변화 event는 기본 크기에서 날짜 rail과 본문이 row를 유지하고 padding 20pt, 답변
  24/36pt, 기록 그룹 간격 32pt를 기준으로 한다.
- 200% 확대에서는 메타와 본문이 자연 높이로 쌓이며 답변·날짜·조작이 겹치거나 잘리지 않는다.
- 삭제 확인은 현재 문장, 전체 버전 삭제 여부, 복구 불가와 공개 화면 영향을 명확히 보여준다.
- 삭제 확인은 원래 화면에 이어 붙인 카드가 아니라 배경 조작을 막는 modal 또는 동등한 전용
  blocking surface로 제공한다. 열릴 때 제목으로 포커스를 옮기고 내부에서만 탐색하며, 취소·실패
  후에는 삭제를 시작한 control로 포커스를 돌려보낸다.

### 공개 선택·미리보기·방문자 화면

- 각 항목은 텍스트와 아이콘으로 `나만 보기` 또는 `공개`를 표시하며 control 높이는 52pt 이상이다.
- 공개 전 확인에는 새로 공개될 현재 문장과 공개되지 않는 과거 기록·작성 맥락을 함께 알린다.
- 미리보기 배너는 프로필 바깥에 있고 종료 행동과 최종 공개 행동이 구분된다.
- 방문자 cover는 별도의 고정 높이 card가 아니라 이름·intro에 맞는 자연 높이 144–220pt의
  `FolioCover`다. 이름·intro와 첫 공개 문장 일부가 첫 viewport에서 함께 읽혀야 한다.
- 미리보기 상단은 경고 banner가 아니라 작은 register와 문구로 앱 chrome과 실제 renderer를
  구분한다. renderer 내부에는 소유자·미리보기 control이 없어야 한다.
- 앱 로고는 공개 화면 footer에 한 번만 표시한다. 외부 header, cover와 footer에 반복하지 않는다.
- 공개 항목이 없어도 정상 프로필로 보이며 비공개 범주 수, 빈 슬롯, 과거 날짜를 유추할 수 없다.

## 시각 시스템 점검

### 타이포그래피

- 같은 역할은 같은 token을 사용한다. 화면별 임의의 20, 21, 22, 23px 제목을 만들지 않는다.
- 기준은 compact nav title 18/26, folio name 34/44, 질문·대표 문장 30/43, 일반 사용자 문장
  24/36, section 18/27, body 16/26, caption 13/20, control 15/22다.
- 질문, 사용자 답변과 공개 profile name은 번들 `MaruBuri` Regular·SemiBold를 사용하고,
  내비게이션·설명·상태·control은 `Pretendard`를 사용한다. 공식 license 파일이 없거나
  임의 시스템 serif로 대체되면 승인하지 않는다.
- 한글 제목 자간은 `-0.02em`을 넘지 않고 본문은 임의의 음수 자간을 사용하지 않는다.
- 줄바꿈은 조사 한 글자나 단어를 고립시키지 않되, 사용자가 입력한 줄바꿈과 원문을 임의로
  교정하지 않는다.
- 200%에서 텍스트가 잘리거나 말줄임으로 핵심 의미가 사라지면 반려한다.

### 간격·정렬·형태

- 390×844는 좌우 20pt gutter와 350pt 콘텐츠 폭, 430×932는 좌우 24pt gutter와 382pt 콘텐츠
  폭을 사용한다. 질문·선택지·입력·행동은 화면 안에서 하나의 세로 기준선을 공유한다.
- 4pt 공간 체계에서 4, 8, 12, 16, 20, 24, 32, 40, 48pt를 우선 사용한다.
- 주요 control은 높이 54pt, 공개 상태 row 52pt, 질문 option은 64pt, 터치 영역은 최소 44×44pt다.
- control radius 12pt, input 14pt, sheet 20pt, modal 24pt를 사용하고 pill은 작은 상태
  레이블에만 사용한다. 모든 콘텐츠를 rounded white card로 감싸지 않는다.
- 사용자 문장 entry는 기본 radius 0, 좌측 3pt register와 entry 사이 1pt rule을 쓴다.
  표면 구분은 1pt rule 또는 배경 차이 중 하나만 사용하고 그림자와 두꺼운 구조선을 쓰지 않는다.
- 콘텐츠와 CTA 사이의 무의미한 빈 공간이 120pt를 넘으면 반려한다. 짧은 화면의 CTA는
  in-flow, 실제 스크롤이 필요한 화면만 sticky action을 쓴다.
- 430pt에서도 단일 열을 유지하며 여분 폭 때문에 카드나 CTA가 내용 폭으로 줄어들지 않는다.
- safe area, 키보드와 하단 내비게이션 때문에 CTA가 가려지지 않는다.

### 색과 브랜드

- Canvas `#F6F3EC`, Paper `#FFFDF8`, Ink `#25231F`, Muted `#68645C`,
  Rule `#918B81`, Rule Soft `#E6E0D5`, Indigo `#4457A6`을 명세 기준으로 사용하고 구현
  token 차이는 승인 없이 늘리지 않는다.
- Indigo·Sage·Apricot은 선택, 범주와 변화의 작은 단서로만 사용하며 화면 면적의 약 10%를 넘지 않는다.
- Scene M의 색, 순서, 비율과 겹침을 바꾸지 않는다. 16–23px에서는 단색, 24px 이상에서만
  조건에 맞는 컬러형을 사용한다.
- `it’sME` 워드마크의 표기·굵기와 보호 여백을 지키고, 로고를 빈 공간을 채우는 장식으로 반복하지 않는다.
- 파스텔 glow, 메시·무지개 그라데이션, 입체 그림자, 얼굴형 로고, 진행 그래프처럼 보이는
  Scene M 변형은 반려한다.
- `FolioGrain`은 canvas에 최대 3% opacity의 단색 tile만 허용한다. 작은 글자·입력·focus와
  고대비 모드에는 적용하지 않으며 얼룩·gradient·먼지 또는 moiré처럼 보이면 반려한다.

## 접근성·인터랙션 게이트

- 일반 텍스트는 4.5:1, 큰 텍스트·아이콘·구조선·포커스 표시는 3:1 이상 대비를 측정한다.
- 입력·버튼·카드 경계, 선택·오류·포커스처럼 구조와 상태를 이해하는 데 필요한 선은 인접
  배경과 3:1 이상이어야 한다. 장식용 divider는 의미 전달에서 제외하거나 텍스트·간격으로
  구조를 보완하며, 낮은 대비의 선에만 정보 구조를 의존하지 않는다.
- 색을 제거해도 활성 탭, 선택지, 공개 상태, 오류와 현재 버전을 구분할 수 있어야 한다.
- 포커스는 3pt Indigo outline과 2pt 이상 offset으로 항상 보이며 레이아웃 크기를 바꾸지 않는다.
- 포커스 순서는 화면의 읽기 순서와 같고, 뒤로가기·닫기·건너뛰기·취소로 안전하게 이탈할 수 있다.
- 장면의 접근성 이름은 `카테고리, 현재 답변, 공개 상태, 마지막 변경일` 순서다.
- 입력 label, 도움말, 글자 수와 오류를 프로그램적으로 연결한다. 저장, 공개 변경과 오류는
  live region 또는 플랫폼 접근성 알림으로 한 번만 전달한다.
- 스크린리더를 켜고 로그인, 질문 저장, 기록 수정, 공개 미리보기와 공개 취소를 완료한다.
- 키보드만으로 Web preview의 같은 여정을 완료하고 포커스가 화면 밖이나 가려진 CTA에 머물지 않는다.
- 축소 모션에서는 위치·크기 변화와 순차 노출을 제거하고 100ms 이하 opacity 또는 즉시 갱신을 사용한다.
- 모션 허용 시에도 화면 진입 180ms, 선택 140ms, 저장 220ms, 공개 변경 180ms 범위를 기준으로
  하며 무한 반복, parallax, 자동 스크롤을 사용하지 않는다.

## 현재 구현 품질 감사

아래는 2026-07-29 기준 `apps/client/src` 코드와 디자인 명세를 대조해 확인한 문제다. 아직
동일 커밋의 필수 실화면 캡처로 재검증하지 않았으므로, 해결 여부는 첫 캡처 묶음에서 다시
판정한다.

이 절은 당시 구현 이력을 보존한다. 2026-08-04의 스프린트 1 실화면 시각 판정과 스프린트 2
변경 기준은 `docs/design/redesign-sprint-2.md`를 따른다. 이 절의 280pt cover, 네 줄 접기와
screen title 수치는 더 이상 현행 승인 수치가 아니다.

### Blocker

1. `/p/{slug}`가 다른 slug로 전환될 때 이전 요청과 다음 요청을 화면 identity별로 격리하거나
   취소하는 보장이 없다. 공유된 `publicProfile` 상태에 이전 사람의 프로필이 잠시 노출되거나,
   늦게 끝난 이전 응답이 현재 slug의 프로필을 덮어쓸 수 있는 요청 경쟁 상태다. slug 변경 즉시
   이전 데이터를 비우고, 응답을 요청 slug와 대조하며, 역순 완료 fixture로 회귀 검증해야 한다.
2. 소유자 `나` cover는 전체 cover에 `나만 보기` badge를 표시하지만 이름과 intro는 실제 공개
   프로필에도 노출된다. 현재 문구는 공개 범위에 대해 거짓 확신을 주므로, 이름·intro 공개 정책을
   PO가 확정하고 필드별 실제 범위를 표시하거나 badge의 적용 대상을 기록으로 한정해야 한다.
3. `timeline.tsx`, `share.tsx`, `preview.tsx`, `p/[slug].tsx`, `record/[id].tsx`의 로딩이
   최종 콘텐츠 구조와 같은 skeleton이 아니라 한 줄 문장이다. 로딩에서 완료 화면으로
   레이아웃이 크게 움직이고 상태 완성도가 화면마다 다르다.
4. 기록 상세의 찾을 수 없음·권한 없음이 하나의 상태로 합쳐져 있고, 공개·상세 화면의
   권한 없음 전용 검증 증거가 없다. 비공개 데이터 영역을 비운 안전한 이탈 상태를 별도로
   확인해야 한다.
5. 소유자·미리보기·방문자 fixture를 함께 비교하는 캡처 게이트가 없어, 비공개 답변과 과거
   맥락이 화면 회귀로 노출되지 않는다는 시각 증거가 없다.

### Major

1. 타이포 위계가 token보다 화면별 숫자로 분산돼 있다. 공용 `Display`는 34/45px인데 명세의
   screen title은 28/38px이고, 실제 화면에는 20·21·22·23·24·30·34px 제목이 혼재한다.
2. `me.tsx` 상단은 월, 계정, 공개 모습 행동이 한 행에서 wrap되고, cover 안에는 54px Scene M과
   나만 보기 badge가 함께 경쟁한다. 390pt와 200% 확대에서 제목과 사용자 문장보다 유틸리티가
   먼저 보일 위험이 있다. cover도 최소 260pt로 명세 280pt와 다르다.
3. `PublicProfileView.tsx` cover는 최소 높이 280pt가 없고 radius 18pt이며, 공개 장면도 최소
   144pt와 답변 24/36pt 기준 대신 22/34px을 사용한다. footer에는 명세된 단일 브랜드 로고가 없다.
4. `timeline.tsx` event padding은 16pt, 답변은 21/32px, 기록 그룹 간격은 24pt로 명세의
   20pt, 24/36px, 32pt보다 조밀하다. 긴 변화 기록에서 읽기 호흡이 약해진다.
5. `share.tsx` 공개 상태 control은 최소 44pt로 구현돼 명세의 52pt보다 낮다. 카드의 답변과
   공개 결정 사이에 충분한 조작 구역이 확보되는지 실화면 확인이 필요하다.
6. `PortraitCanvas.tsx`와 `PublicProfileView.tsx`는 긴 답변의 네 줄 접기·`이어 읽기`가 없다.
   짧은 답과 긴 답의 카드 리듬이 크게 달라지고 주요 CTA가 과도하게 밀릴 수 있다.
7. 선택형 질문은 체크 아이콘과 접근성 상태는 있지만 화면에 `선택됨` 의미가 명시되지 않고,
   자유 입력에는 현재 글자 수가 없다. 선택 후 점진적 맥락 입력도 구현에서 확인되지 않는다.
8. 공용 색 token의 Paper, Ink, Line, Brand Soft와 Error 값이 확정 디자인 명세 값과 다르다.
   작은 차이를 계속 허용하면 화면별 경계·대비·브랜드 인상이 더 분산된다.
9. 질문과 기록 화면에서 600자 답변과 200% 확대를 함께 검증하는 fixture와 캡처가 없다. 긴
   입력이 키보드, 글자 수, 오류와 하단 행동을 밀어내거나 접근 순서를 깨뜨릴 위험이 있다.
10. 기록 삭제 확인은 현재 화면의 콘텐츠 흐름 안에 이어 붙는 카드다. 삭제 대상이 길면 확인
    문장과 영구 삭제 행동이 서로 다른 viewport에 놓이고, modal의 배경 조작 차단·포커스
    가두기·닫은 뒤 포커스 복귀가 보장되지 않는다.
11. `colors.line`을 사용하는 입력·카드·구분선이 흰 배경에서 구조선 기준 3:1을 충족한다는
    측정 결과가 없다. 특히 focus가 기본 outline을 제거하고 border 변경에 의존해 상태 경계가
    낮은 대비 또는 레이아웃 변화로 나타날 수 있다.
12. 정상·상태·두 뷰포트·200% 확대의 기준 이미지를 같은 fixture로 비교하는 시각 회귀 CI가
    없다. 공용 token이나 renderer 변경이 인접 화면을 깨뜨려도 기능 테스트만으로는 발견하기 어렵다.

### Minor

1. 공용 공간 token에 12, 20, 48pt가 없어 여러 화면이 magic number를 사용한다. 동일한 역할의
   padding과 gap이 다음 변경에서 다시 달라질 가능성이 높다.
2. 일부 포커스는 외곽선과 offset 대신 컴포넌트 border를 2px로 바꾼다. 키보드 포커스에서
   크기 변화와 3:1 대비를 실화면으로 확인해야 한다.
3. `나`의 화면 제목 `내 프로필`, 변화 화면의 설명과 일부 빈 상태 문구가 확정 명세의 핵심
   언어와 다르다. 기능 의미는 유지되지만 네 탭 사이의 목소리와 제목 위계가 일관되지 않다.

우선순위는 Blocker의 상태·프라이버시 증거, Major의 타이포·커버·긴 콘텐츠, 화면별 간격과
상태 control, Minor의 token 정리 순서다. 시각 개편 전에 이 순서로 기준을 회복해야 스타일
수정이 또 다른 불일치를 만들지 않는다.

## 레퍼런스 사용 원칙

- 레퍼런스마다 출처, URL, 확인 날짜와 차용하려는 원리 한 가지를 기록한다. 화면 전체를
  `비슷하게` 만드는 요청은 허용하지 않는다.
- 차용 대상은 입력 부담, 한글 위계, 여백, 짧은 기록의 편집 리듬, 점진적 공개와 상태 전달 방식이다.
- 리틀리의 적은 블록, 문토의 생활 언어, 왓챠피디아의 점진적 입력, 브런치스토리·29CM의
  편집 리듬, 하루콩·세줄일기의 낮은 기록 부담을 참고할 수 있다.
- 좋아요, 별점, 팔로워·구독자, 조회수, 인기·추천 순위, 판매·후원, 모임 규모, 연속 기록,
  프로필 완성도와 알고리즘 점수는 레퍼런스에 있더라도 가져오지 않는다.
- 레퍼런스의 색·아이콘·카드 배치를 그대로 복제하지 않고 `나의 장면` 토큰과 Scene M 브랜드
  규칙으로 다시 설계한다. 라이선스가 불명확한 이미지와 아이콘은 제품 자산에 포함하지 않는다.
- AI가 생성한 시안은 아이디어 탐색 증거일 뿐 최종 레퍼런스나 접근성 증거가 아니다. 실제
  한글 콘텐츠, 긴 답변, 빈 상태와 200% 확대를 넣은 구현 화면으로 다시 검증한다.

## 자동 반려 기준

다음 중 하나라도 해당하면 다른 장점과 관계없이 디자인 승인을 반려한다.

- 좋아요, 팔로워·팔로잉, 조회수, 인기·강점 순위, 궁합·성장 점수, 완성률, 경쟁형 연속 기록이 있음
- 비어 있는 범주를 결핍·미완성으로 표현하거나 질문을 건너뛰기·닫기·나중에 수정할 수 없음
- 새 기록이 공개로 시작하거나 공개 전 실제 방문자 결과를 확인할 수 없음
- 미리보기와 방문자 화면이 다르거나 비공개 답변·범주 자리표시·과거 버전·작성 맥락이 노출됨
- `/p/{slug}` 전환 중 이전 사람의 공개 프로필이 보이거나 늦게 끝난 이전 응답이 현재 화면을 덮어씀
- 소유자 cover의 공개 범위 문구가 실제로 공개되는 이름·intro·기록의 범위와 일치하지 않음
- 필수 뷰포트·상태·200% 확대 캡처가 누락되거나 잘림, 겹침, 가로 스크롤, 가려진 CTA가 있음
- 600자 답변과 200% 확대·키보드 동시 조건에서 글자 수, 오류, 저장 또는 건너뛰기를 읽고 조작할 수 없음
